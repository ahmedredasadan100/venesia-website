# VENESIA_CMS_RULES.md
# النسخة الموحدة والمنظفة
# Unified Refactor Edition

---

## 1. المهمة (Mission)

بناء نظام إدارة محتوى (CMS) قابل لإعادة الاستخدام والتوسع. Venesia هي أول تطبيق، لكن ليست الهدف الوحيد.

---

## 2. المبادئ الأساسية (Core Principles)

| المبدأ | الشرح |
|--------|-------|
| **Data First, Not Page First** | التفكير في كيانات (Entities) وليس صفحات منفصلة |
| **Fix the Component, not the Page** | إصلاح العنصر المشترك مش الصفحة الواحدة |
| **Reuse Before Create** | إعادة الاستخدام قبل الإنشاء |
| **Database First** | البيانات في Supabase، مش ملفات ثابتة |
| **Single Source of Truth** | هذا الملف هو المرجع الوحيد المعتمد |
| **Architecture > Speed** | إذا تعارضت السرعة مع جودة المعمارية، تُقدَّم جودة المعمارية |

---

## 3. Golden Rule

> أي عنصر يظهر في **صفحتين أو أكثر**، يتحول إلى **Shared Component واحد**، ويمنع:
> - نسخه داخل صفحة منفردة
> - تعديل شكله محليًا داخل صفحة واحدة
> - إنشاء Variant خاص بدون سبب معماري واضح
> - إصلاح نفس المشكلة في أكثر من ملف

---

## 4. الكيانات (Entities)

كل كيان له: Data Model + Admin Page + Shared UI + CRUD + Status + Search/Sort/Filter

```
Article    | Category  | Series   | Media    | Project
Page       | Block     | User     | Role     | Setting
```

## 8. بطاقة التعريف (Page Hero)

**النمط المعتمد:**
```
Admin Panel
إدارة + [اسم الكيان]
[وصف مختصر]
```

**أمثلة:**
- `Admin Panel` / `إدارة السلاسل` / `السلاسل كيان مستقل لتنظيم الموضوعات في رحلات قراءة مترابطة`
- `Admin Panel` / `إدارة المقالات` / `المقالات هي وحدة المحتوى الأساسية`

**أزرار الإنشاء** توضع داخل الصفحة بجوار العنوان، مش في الهيدر.

## 9. محرك الجداول (AdminDataGrid)

### 9.1 الاستخدام الإجباري
كل جداول الأدمن **لازم** تستخدم `AdminDataGrid`. يمنع إنشاء Table محلي.

### 9.2 الترتيب (Sorting)
الأعمدة الأساسية لازم تدعم:
- تصاعدي (Ascending)
- تنازلي (Descending)
- الرجوع للافتراضي (الضغطة الثالثة)

### 9.3 محاذاة الأعمدة (Alignment)

| نوع العمود | المحاذاة |
|------------|----------|
| نصوص / Layout مخصص (أيقونة+اسم) | بداية المحتوى (start) |
| رقمي (عدد الموضوعات، المشاهدات) | وسط (center) |
| الحالة (Status) | متطابقة مع مكان الـ Status Pill |
| الإجراءات (Action) | Layout ثابت على مستوى النظام |

> **الأولوية:** الاتساق البصري (Visual Alignment) مش التوسيط الهندسي.

### 9.4 عرض الأعمدة (Column Width)

| نوع العمود | العرض |
|------------|-------|
| نصوص | أكبر مساحة |
| رقمي | أقل عرض مناسب |
| الحالة | متوسط (يناسب Status Pill) |
| الإجراءات | ثابت موحد |
| مساحة فارغة غير مبررة | يُزال لتحسين كثافة المعلومات |

## 10. التحديد الجماعي (Checkbox & Bulk Actions)

**السلوك المعتمد:**
- Checkbox selection → Bulk Action Bar يظهر أعلى الجدول
- نفس الشكل / نفس المكان / نفس الأزرار / نفس الحركة

**ممنوع:**
- تغيير مكانه في صفحة واحدة
- تغيير تصميمه محليًا
- إنشاء Bulk Bar جديد داخل صفحة منفردة

---

## 11. أزرار الإجراءات (Action Buttons)

تستخدم `AdminActionButton` المشترك. يجب أن تكون متطابقة في:
- الحجم / المسافات / الألوان / الـ hover / ترتيب الظهور / مستوى الوضوح

**الأزرار:**
```
عرض | تعديل | نسخ | حذف | إخفاء | نشر
```

---

## 12. الحالات (Status)

يُستخدم `AdminStatusPill` فقط. يمنع Badge محلي أو ألوان مختلفة.

```
منشور | مسودة | مخفي | مؤرشف | نشط | غير نشط
```

---

## 13. نافذة الإجراءات (Venesia Action Modal)

للإجراءات المتقدمة بدلًا من Dropdowns الضيقة:
- إدارة عناصر مرتبطة
- تغيير حالة متقدمة
- مراجعة تفاصيل قبل التنفيذ
- إجراءات جماعية تحتاج تأكيدًا

---

## 14. التحديث الذكي للجداول (Table-Scoped Updates)

أي إجراء (CRUD / Sorting / Filtering / Search / Bulk Actions / Pagination / Toggle Status) يجب أن:
- يحدّث الجدول نفسه فقط
- **بدون** إعادة تحميل الصفحة بالكامل
- مع الحفاظ على حالة المستخدم (الصفحة، الفلاتر، التحديد)

---

## 15. الصفحات: الحديثة vs القديمة

| Modern | Legacy | Needs Migration |
|--------|--------|-----------------|
| AdminDataGrid | Table محلي | يجب تحويلها |
| AdminStatusPill | Badge محلي | |
| AdminActionButton | Buttons محلية | |
| AdminBulkActionBar | | |
| useAdminGridSelection | | |
| Shared Page Hero | Header قديم | |

**قاعدة:** لا يتم تطوير Features جديدة فوق صفحة Legacy قبل تحويلها أو وضع خطة تحويل واضحة.

---

## 16. قواعد قاعدة البيانات (Database Rule)

البيانات القابلة للإدارة من CMS **لازم** تكون في Supabase، مش:
- ملفات TypeScript
- Arrays ثابتة
- Hardcoded Data

---

## 17. لا يوجد تصميم محلي (No Local Styling)

**مسموح للصفحة أن تمرر:**
- title / description / columns / rows / actions / filters / empty state text

**ممنوع أن تعيد بناء:**
- الجدول / الهيدر / أزرار الإجراءات / شريط الإجراءات الجماعية / Status Pills / Pagination

---

## 18. قواعد الملفات (File Hygiene)

**ممنوع داخل المشروع:**
```
file.tsx1    file.tsx2    backup.tsx    old.tsx    copy.tsx
```

**النسخ الاحتياطية:** عبر Git فقط أو خارج مجلد المشروع.

---

## 19. قواعد الاستيراد (Import)

```tsx
import { AdminDataGrid, AdminStatusPill, AdminActionButton } from "@/components/admin/ui";
```

يمنع تكرار نفس الـ Component بأسماء مختلفة في مسارات متعددة.

---

## 20. سير العمل (Development Workflow)

قبل أي تعديل:
1. تحديد Modern vs Legacy
2. تحديد الـ Shared Components المستخدمة
3. منع أي تعديل محلي على عناصر عالمية
4. تنفيذ التعديل في Component مشترك إن أمكن
5. اختبار تأثير التعديل على الصفحات الأخرى
6. توثيق أي قاعدة جديدة هنا

---

## 21. قائمة التحقق قبل الـ Commit (Before Merge Checklist)

- [ ] لا يوجد Hardcoded Data غير مبرر
- [ ] لا يوجد Duplicate Components
- [ ] لا يوجد Backup Files داخل المشروع
- [ ] يستخدم Shared UI
- [ ] لا يكسر أي صفحة أخرى
- [ ] متوافق مع VENESIA_CMS_RULES
- [ ] تم اختبار Shared Component على كل الصفحات التي تستخدمه

---

## 22. ثلاثة اختبارات قبل أي Commit

1. **هل يمكن تحويله إلى Shared Component؟**
2. **هل سيؤثر على بقية الصفحات؟** → إذا نعم، التعديل في الـ Shared Component
3. **هل يكسر التناسق البصري أو السلوكي؟** → إذا نعم، يُعاد تصميمه

---

## 23. نظام الأولويات (Priority System)

| Critical | Important | Later |
|----------|-----------|-------|
| مشاكل تكسر النظام | تحويل Legacy → Modern | تحسينات جمالية |
| ملفات فوضوية / نسخ احتياطية | توحيد الجداول والأزرار والـ Status | تحسينات Dashboard |
| Components عالمية يتم تكرارها محليًا | تحسين تدفق البيانات | Refactor غير مؤثر |
| UI غير متسق في عناصر أساسية | | محرر المحتوى (مرحلة مستقلة) |

---

## 24. الصفحة المرجعية (Reference Page)

```
/admin/content/series = المرجع الأساسي للجداول والإدارة
```

أي صفحة جديدة يجب أن تحاكي هذا النمط. لا يتم اختراع Pattern جديد إلا إذا أصبح Shared Component.

---

## 25. القرارات المعتمدة حاليًا (Current Approved Decisions)

1. الهيدر العام يحمل فقط `Admin Panel`
2. حذف البحث من الهيدر العام
3. حذف زر جديد / مقالة جديدة من الهيدر العام
4. أزرار الإنشاء داخل الصفحات نفسها
5. إزالة اللوجو من الـ Sidebar
6. إزالة "الأقسام" من الـ Sidebar
7. Page Hero يستخدم `Admin Panel` كتعريف صغير
8. عنوان الصفحة: `إدارة + اسم الكيان`
9. الجداول تعتمد على `AdminDataGrid`
10. الأعمدة الأساسية تدعم Sorting
11. Checkbox و Bulk Action Bar لا يتم تغييرهما
12. صفحة السلاسل هي Reference أولي بعد التعديلات

---

## 26. قاعدة عدم كسر التغييرات (No Breaking Changes)

أي تعديل على Shared Component يجب اختباره على **جميع** الصفحات التي تستخدمه.

لا يجوز تعديل Component مشترك لحل مشكلة في صفحة واحدة إذا كان سيكسر صفحات أخرى.

---

## 27. القاعدة النهائية (Final Rule)

> **لا يتم إصلاح الشكل صفحة بصفحة.**
> **يتم إصلاح النظام من مصدره.**
>
> `Fix the Component, not the Page.`

---

## 28. المرجع الرسمي الوحيد (Single Source of Truth)

هذا الملف هو المرجع الرسمي الوحيد للمشروع.

أي قاعدة جديدة تخص: Architecture / UI / Shared Components / Naming / Workflow / Admin Behavior

يجب إضافتها هنا، ولا يتم إنشاء ملفات Rules جديدة إلا عند الضرورة القصوى.

---

## 29. قاعدة AI / Cursor

أي AI Assistant أو Cursor يعمل على المشروع يجب أن:
1. يقرأ `VENESIA_CMS_RULES` أولًا
2. يعتبره المرجع الأعلى قبل أي تعديل

---

## 30. القاعدة الذهبية الأخيرة

> **إذا تعارضت السرعة مع جودة المعمارية، تُقدَّم جودة المعمارية.**
> **نفضّل تنفيذًا صحيحًا مرة واحدة على ترقيعات متكررة.**

---

## 31. اتجاه UI المعتمد (Approved Admin UI Direction)

Venesia CMS يجب أن يظهر كمنصة:
- هادئة / منظمة / فاخرة بدون زحمة
- مبنية على مكونات موحدة / سهلة التوسع
- لا تعتمد على ترقيع صفحة بصفحة

> **الهدف:** أي صفحة جديدة يجب أن تبدو وكأنها جزء طبيعي من نفس النظام، لا صفحة منفصلة تم تصميمها من الصفر.



---
## 32. لا يوجد شخصية مستقلة للصفحات

الصفحات الإدارية ليس لها شخصية مستقلة.

أي صفحة جديدة يجب أن تبدو وكأنها جزء طبيعي من نفس النظام، ولا يجوز تغيير شكل الجداول أو الأزرار أو الـ Toolbar أو الـ Bulk Actions بشكل محلي داخل صفحة واحدة.

---

## 33. محرك الجداول الإداري (Admin Table Engine)

جميع الجداول تعتمد على **Admin Table Engine**.

وهو المسؤول عن:
- Search
- Sorting
- Filtering
- Pagination
- Selection
- Bulk Actions
- Table Refresh
- Loading
- Feedback

ولا يجوز لأي صفحة أن تعيد تنفيذ هذا المنطق محليًا.

> **القاعدة:** لا يجوز لأي صفحة أن تبني محرك جدول خاص بها. كل الجداول تمر عبر Admin Table Engine.

---

## 34. AdminDataGridSortLabel

إذا احتاجت عدة صفحات إلى نفس سلوك محاذاة عناوين الأعمدة، فيجب تطوير **AdminDataGridSortLabel** ليدعم:

```tsx
align="start"   // للأعمدة النصية
align="center"  // للأعمدة الرقمية
align="end"     // للأعمدة التي تنتهي من اليمين
```

بدلاً من إضافة Wrappers محلية في كل صفحة.

> **القاعدة:** أي Wrapper لمحاذاة عمود يُعتبر Technical Debt إذا تكرر في أكثر من صفحة.

---

## 35. قاعدة الديون التقنية (Technical Debt Rule)

أي حل مؤقت محلي (مثل Wrapper لمحاذاة عمود معين) يجب اعتباره **Technical Debt** ونقله إلى **Shared Component** إذا تكرر في:
- صفحتين أو أكثر
- أو إذا كان من المتوقع تكراره في المستقبل

**الخطوات:**
1. تحديد الحل المؤقت
2. تسجيله كـ Technical Debt في الملف أو التعليقات
3. تحويله إلى Shared Component في أقرب فرصة
4. إزالة النسخ المحلية واستخدام الـ Shared Component

---

## 36. قاعدة كثافة التخطيط (Layout Density Rule)

لا يجوز ترك فراغات كبيرة غير مبررة داخل الجداول.

عرض الأعمدة يجب أن يعتمد على **نوع البيانات** وليس على التقسيم المتساوي.

| نوع البيانات | السلوك |
|-------------|--------|
| نصوص طويلة | أقصى عرض ممكن |
| أرقام / عدادات | أقل عرض مناسب |
| حالات (Status) | عرض يناسب الـ Pill |
| إجراءات (Actions) | عرض ثابت موحد |
| مساحة فارغة غير مبررة | تُزال أو تُضغط |

> **الهدف:** تحسين كثافة المعلومات (Information Density) بدون إرباك المستخدم.

---

## 37. محرك الجداول > إعادة التحميل الكامل (Admin Table Engine > Full Reload)

أي عملية CRUD أو Sorting أو Filtering يجب أن تحدث على **مستوى الجدول نفسه** دون إعادة تحميل الصفحة بالكامل متى أمكن.

**السلوك المطلوب:**
- تحديث الصفوف المؤثرة فقط
- الحفاظ على حالة المستخدم (الصفحة، الفلاتر، التحديد)
- إعادة جلب البيانات عبر API إذا لزم الأمر
- عدم فقدان سياق المستخدم

**ممنوع:**
- `window.location.reload()`
- `router.refresh()` كامل للصفحة
- فقدان حالة التحديد بعد عملية
- فقدان موضع التمرير (Scroll Position)
